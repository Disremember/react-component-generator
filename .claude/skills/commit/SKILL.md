# commit: 변경사항 분석 → 논리 단위 분리 → 즉시 커밋

변경사항을 읽고 **리뷰어가 커밋 하나만 보고도 의도를 알 수 있도록** 묶어서 커밋한다. 사용자는 커밋 요청 자체로 실행을 승인한 것이므로, 계획을 보여주고 확인을 기다리지 말고 바로 커밋한 뒤 결과를 보고한다. 로컬 커밋은 `git reset --soft HEAD~N`으로 되돌릴 수 있지만, 이력에 들어간 인증정보는 지워도 남으므로 아래 제외 규칙만큼은 승인 단계가 없는 대신 더 엄격히 지킨다.

## Step 1: 상태 확인과 변경사항 분석

```bash
git rev-parse --is-inside-work-tree   # 저장소가 아니면 사용자에게 알리고 중단
git status --short
git diff --staged --stat && git diff --stat
git diff --staged && git diff          # 실제 내용
git log --oneline -10                  # 기존 메시지 스타일 참고
```

- 새 파일(untracked)은 diff에 안 나오므로 `git status`로 확인하고 필요하면 내용을 읽는다.
- 사용자가 이미 일부를 stage해 두었다면 그 선택에 의도가 있다고 보고, stage된 파일을 첫 커밋으로 먼저 커밋한다(필요하면 그 안에서만 다시 나눈다).
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- 머지/리베이스 진행 중(`.git/MERGE_HEAD`, `rebase-merge/` 존재)이면 일반 커밋 흐름과 다르므로 상황을 알리고 사용자 지시를 받는다.

### 커밋하면 안 되는 파일 걸러내기

다음은 커밋 대상에서 빼고, 결과 보고에 "제외됨 + 이유"로 표시한다. 한 번 이력에 들어가면 지워도 남기 때문이다.

- 인증정보가 들어갈 수 있는 파일: `.env*`, `*.pem`, `*.key`, `id_rsa*`, `credentials*`, 토큰이 하드코딩된 설정 등
- diff 안에서 비밀번호·API 키·토큰·개인키·DB 접속 문자열처럼 보이는 값을 발견한 경우 → 해당 파일을 제외하고 **값은 출력하지 말고 위치(파일명:행)만** 알린다.
- 빌드 산출물·의존성·로그(`dist/`, `node_modules/`, `*.log`)가 `.gitignore`에서 빠져 있어 잡힌 경우 → `.gitignore` 추가를 제안한다.

## Step 2: 논리적 단위로 분류

"이 커밋만 revert해도 나머지가 정상 동작하는가"를 기준으로 묶는다.

- 하나의 기능 추가와 그 테스트·타입·스타일 변경은 **같은 커밋**이다.
- 기능과 무관한 리팩터링, 버그 수정, 의존성/설정 변경은 **별도 커밋**으로 나눈다.
- 한 파일 안에 성격이 다른 변경이 섞여 있으면 `git add -p` 대신 파일 단위로 판단해 주된 목적의 커밋에 넣고, 섞여 있었다는 사실을 결과 보고에 적는다(대화형 명령은 쓸 수 없다).
- 변경이 작고 한 가지 목적이면 억지로 쪼개지 말고 커밋 1개로 둔다.

## Step 3: 커밋 메시지 작성

형식: `<type>: <한국어 요약>`

| type | 언제 |
|------|------|
| `feat` | 사용자가 체감하는 새 기능·동작 추가 |
| `fix` | 버그 수정, 잘못된 동작 교정 |
| `refactor` | 동작 변화 없는 구조 개선, 이름 변경, 중복 제거 |
| `chore` | 빌드·설정·의존성·문서·스크립트 등 그 외 |

- 요약은 50자 안팎, 마침표 없이, "~추가", "~수정"처럼 명사형으로 끝낸다. 무엇을 바꿨는지보다 **왜/무엇이 달라지는지**가 드러나게 쓴다.
- 요약만으로 부족하면 한 줄 띄우고 본문에 이유나 주요 변경점을 2~4줄로 적는다.
- `git log`의 기존 스타일(scope 사용 여부 등)이 위 형식과 다르면, 위 형식을 기본으로 하되 결과 보고에서 차이를 알려준다.
- 세션 지침에 커밋 attribution(예: `Co-Authored-By:` 줄)이 있으면 본문 끝에 붙인다.

예시:
- `feat: 컴포넌트 생성 폼에 props 기본값 입력 추가`
- `fix: 빈 컴포넌트 이름 입력 시 서버 500 오류 수정`
- `refactor: 코드 생성 로직을 generator 모듈로 분리`
- `chore: eslint 규칙에 react-hooks 플러그인 추가`

## Step 4: 바로 커밋 → 결과 보고

확인 질문 없이 분류한 순서대로 커밋한다. 커밋마다 해당 파일만 명시적으로 stage한다. `git add -A`/`git add .`는 제외 파일까지 들어가므로 쓰지 않는다.

```bash
git add -- <파일들>
git commit -m "<요약>" -m "<본문(선택)>"
```

- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 말고, 남은 커밋을 멈춘 뒤 오류와 그때까지 만든 커밋을 보고한다. 훅이 파일을 자동 수정했다면 다시 stage해서 새로 커밋한다(`--amend` 금지: 직전 커밋을 덮어쓴다).
- 끝나면 `git log --oneline -n <커밋 수>` 결과와 함께 아래처럼 보고한다. push는 사용자가 따로 요청할 때만 한다.

```
커밋 2개 완료

a1b2c3d feat: 컴포넌트 생성 폼에 props 기본값 입력 추가
        - src/components/GeneratorForm.tsx, src/types/component.ts
e4f5g6h chore: eslint 규칙에 react-hooks 플러그인 추가
        - eslint.config.js, package.json, bun.lock

제외: .env (인증정보 포함 가능)
되돌리려면: git reset --soft HEAD~2
```
